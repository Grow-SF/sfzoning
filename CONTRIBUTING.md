# How to contribute

Thanks for helping. Useful contributions include:

- **Fixing a map.** A district read wrong, a sheet aligned badly, a seam or
  stray line on the paper scans. Open an issue with the year, the place and a
  screenshot, or fix it yourself (see below).
- **Correcting the history.** The story text and the research table
  (`docs/research/zoning-districts.csv`) cite their sources. If you have a
  better source, or spot an error, open an issue or a pull request with the
  citation.
- **Improving the site or the pipeline.** Bugs, accessibility, performance, docs.
- **Bringing this to your city.** The pipeline aligns scanned historic maps to
  modern GIS data. If you're adapting it, open an issue: we'd like to hear
  what you needed to change, and generalizing it is welcome.

## 1. Agree to the CLA (once)

GrowSF asks every contributor to agree to the
[GrowSF Individual Contributor License Agreement](CLA.md), adapted from the
Apache Software Foundation's ICLA. You keep the copyright in your work; the
agreement gives GrowSF a license to use it and lets GrowSF keep the project's
licensing flexible.

To agree, post this comment on your first pull request, exactly as written:

> I have read the GrowSF Individual Contributor License Agreement (CLA.md,
> version 1.0) and I agree to it for all my present and future contributions
> to GrowSF.

Pull requests can't be merged until the author has posted it. If your employer
has rights in your work, make sure you're permitted to contribute (CLA
section 4); for contributions owned by a company, contact GrowSF.

## 2. Set up

Fork the repository, clone your fork, and set up the part you're working on.

### The site (`site/`)

You need Node.js 22 or later. You don't need to build any map tiles: point
your dev server at the published ones.

```sh
cd site
npm install
NEXT_PUBLIC_TILES_BASE_URL=https://zwgxwpoxqzfauqfg.public.blob.vercel-storage.com npm run dev
```

Then open http://localhost:3000. See `site/README.md` for more.

### The pipeline (`pipeline/`)

You need Python 3.12, [uv](https://docs.astral.sh/uv/), and GDAL 3.13 or
later, pmtiles and poppler (`brew install gdal pmtiles poppler` on macOS).

```sh
cd pipeline
uv sync
uv run pytest
```

The tests use synthetic fixtures and need no data or API key. Working with the
real maps needs the scans and processed files; see "Recreate without
re-running" in `pipeline/README.md`. Reading map labels and districts calls the
OpenAI API (your own key, in `pipeline/.env`) and costs money; cached answers
are reused, so most work doesn't need it.

## 3. Make your change

1. Create a branch from `main`.
2. Make your change. Keep each pull request to one change, and add or update
   tests for code changes.
3. Run the tests for what you touched:
   - site: `npm test` and `npx playwright test` in `site/`;
   - pipeline: `uv run pytest` in `pipeline/`.
4. Open a pull request against `main`. Say what changed and why; for map or
   history fixes, include the source or a screenshot.

## 4. Review and release

- Every pull request gets a **preview deployment** of the site automatically;
  Vercel posts its link on the pull request. Use it to check your change.
  Previews are visible to GrowSF's Vercel team.
- A maintainer reviews the change. Once it's merged into `main`, it deploys to
  https://www.sfzoning.com automatically.
- Changes to map tiles or district data are published separately by a
  maintainer, since the tiles are generated by the pipeline rather than stored
  in this repository.

## Ground rules

- Never commit secrets: API keys, tokens, `.env` files.
- Don't commit generated data (`pipeline/data/`). It's shared through the
  processed bundle instead.
- Keep the credits: the attribution to Steven Bacio and GrowSF, and the
  third-party credits in `NOTICE`, must stay.
